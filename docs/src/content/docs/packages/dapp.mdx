`@sigilry/dapp` is the core package for [CIP-103](https://github.com/canton-foundation/cips/blob/main/cip-0103/cip-0103.md)-compliant dApp ↔ wallet extension communication on Canton Network. It provides the CIP-103 provider interface (`SpliceProvider`), JSON-RPC client and server, transport abstractions, and Zod schemas generated from the CIP-103 OpenRPC spec.

## Install

```bash
yarn add @sigilry/dapp@^3
```

Use the stable 3.x line on `latest`. Partner guides cover [Send Connect testnet](/guides/send-connect-testnet/), [verifying signMessage](/guides/verify-sign-message/), and [reading holdings](/guides/read-holdings/).

## Provider discovery

When more than one Canton wallet may be present, dApps should discover providers instead of reaching for `window.canton` directly. The discovery primitives live on the `@sigilry/dapp/discovery` subpath — they are intentionally **not** re-exported from the package root. See [Provider Discovery](/concepts/discovery/) for the model and fallback semantics.

## Push events

A `SpliceProvider` delivers the CIP-103 push events through the EIP-1193-style `.on()` API — the §4.2.2 sync events (`accountsChanged`, `statusChanged`, `txChanged`) plus the `connected` login event. `WindowTransport` carries notifications inbound on the same channel as requests (a notification is an id-less frame; the JSON-RPC `id` is the direction discriminant), and `SpliceProviderBase` auto-wires them to the provider's emitter — so a provider from `createProvider` (or the injected `window.canton`) emits with no extra setup.

<Snippet path="dapp/events.ts" />

On the wallet (server) side, emit notifications with `notify(event, payload, target?)` on the transport. Frames whose `target` does not match a provider's configured target are filtered out, so multi-wallet pages never cross-deliver events. See [CIP-103 Conformance](/concepts/cip-103-conformance/) for the normative event semantics.

## Generated schemas

Zod schemas are generated from OpenRPC specifications and exposed under `@sigilry/dapp/schemas`:

<Snippet path="dapp/schemas.ts" />

`SignMessageResultSchema` requires `signature` and accepts optional `signedBy`,
`publicKey` (base64 DER SPKI), `signingAlgorithmSpec` (`"ed25519" | "ecdsa-sha256"`),
`format` (`"concat" | "der"`), and `encoding` (`"base64" | "hex"`). Some wallets, including a pending
Send release, may include these fields; they are not yet part of CIP-0103. Signature-only results remain valid; unknown keys are
rejected. The inferred `SignMessageResult` type carries the same optional fields. See
[Verify signMessage](/guides/verify-sign-message/) for the Send Connect extension's format, metadata availability, and key
authorization considerations.

Regenerate schemas after spec updates:

```bash
yarn workspace @sigilry/dapp codegen
```
