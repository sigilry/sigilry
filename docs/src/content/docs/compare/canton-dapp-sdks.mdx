description: A sourced comparison of Sigilry, the Canton dApp SDK, PartyLayer, and the Console Wallet dApp SDK.

Choose the integration layer that fits the application: Sigilry's typed provider toolkit, DA's wallet-discovery SDK, PartyLayer's native provider with an adapter bridge and UI components, or a Console-focused SDK. These are different documented integration surfaces, not a ranking. [Sigilry][S], [Canton dApp SDK][D], [PartyLayer][P], [Console][C].

## Scope and versions

Snapshot checked **2026-10-05** with `npm view`:

- Sigilry: [`@sigilry/dapp` 3.4.0][S-meta], [`@sigilry/react` 3.2.2][S-react-meta], and [`@sigilry/cli` 0.3.3][S-cli-meta].
- DA: [`@canton-network/dapp-sdk` 1.7.1][D-meta]. This is the official Canton dApp SDK linked from [Canton's introduction to CIP-0103][D-official] and documented in the [Canton developer docs][D].
- PartyLayer: [`@partylayer/sdk` 0.19.0][P-meta]. The cells below describe documentation at [source commit `c0d6ddd`][P], not verified behavior of that npm release or every PartyLayer package.
- Console: [`@console-wallet/dapp-sdk` 2.4.0][C-meta], with its [versioned README][C] and [distributed type declarations][C-types].

Sigilry source links are pinned to public mirror commit `c264b6e`; DA source links are pinned to `d8b41d9`. Website documentation describes the pages inspected on the snapshot date and can change independently of npm releases.

**Documented** means a maintainer describes the capability. **Unknown** means the named capability was not established by the cited sources; it does not mean unsupported. This comparison is based on documentation, source, and package metadata. It does not establish interoperability, conformance certification, relative performance, or successful installation in a particular application.

## Choose by required surface

The following fit guidance is an editorial interpretation of the documented surfaces, not a result of comparative testing:

- Evaluate **Sigilry** when the application needs explicit typed RPC/provider building blocks, custom transports, and its React layer. [dApp][S], [transports][S-transport], [React][S-react].
- Evaluate **DA's official SDK** when the framework-independent wallet picker and remote-wallet adapters fit the onboarding flow. Its Web Component supplies a documented UI without requiring React-specific hooks. [Canton introduction][D-official], [README][D-source], [discovery][D-discovery].
- Evaluate **PartyLayer** when the native provider, adapter bridge, and ready-made React modal/button fit. Select the native or bridge path deliberately: the inspected README documents different async and ledger behavior. [Provider][P-provider], [README][P], [React][P-react].
- Evaluate **Console's SDK** for Console-specific accounts, queries, mobile QR/deep links, and its additional signing/encryption APIs. [README][C].

## Separate SDK capability from wallet capability

An adapter or transport does not establish that every wallet supports every method or network. PartyLayer explicitly gates typed transfers by wallet capability; DA documents adapter registration and discovery configuration. [PartyLayer transfer guide][P-transfer], [DA discovery][D-discovery].

For the actual package, wallet version, and network, record the results of this integration checklist:

1. Discover/select the intended wallet and connect.
2. Observe account, network, and connection changes.
3. Read application data through the intended ledger path.
4. Request and verify a signed message using that wallet's documented algorithm, encoding, and key authorization rules.
5. Handle user rejection and unsupported methods.
6. Submit a representative transaction and observe completion or failure.
7. Tear down listeners, disconnect, and test session restoration where offered.

This checklist is proposed verification work; no results are asserted for the four SDKs here. A reproducible integration recipe should pin the package, wallet, and network versions and report these outcomes after it has been run.

## Understand the type boundary

Typed RPC envelopes, generated Daml record types, and generated action functions are separate layers. Sigilry documents typed provider/RPC calls and a CLI wrapping `dpm codegen-alpha-typescript`. Those sources alone do not establish a shipped workflow that generates a choice action from a DAR and executes it through a wallet. PartyLayer's documented transfer intent is another abstraction: the wallet receives a transfer request, subject to capability support. [Sigilry dApp][S], [CLI][S-cli], [codegen][S-codegen], [PartyLayer transfers][P-transfer].
